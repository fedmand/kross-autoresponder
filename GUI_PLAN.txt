Kross Autoresponder — GUI Plan
==============================

Goal
----
An Airbnb-style dashboard for hosts to review notifications produced by the AI
bot (escalations only), filter them, and mark them as handled.

Branch split
------------
- Colleague's branch: produces & stores notifications (the data / backend).
- My branch (GUI): reads & displays notifications, lets host act on them.

CONFIRMED DECISIONS
-------------------
1. Scope: the dashboard shows ONLY notifications that require host intervention
   (the bot's escalations). "Tutti" = all interventions.
2. Filter model: category (single-select) + facets (combinable) + sort.
   Categories (3): Tutti / Riparazioni / Early-late check-in/out.
   Sidebar order: Stato (date) first, then Categoria.
3. booking_status (passata/presente/futura) computed by the GUI from
   check_in/check_out vs today.
4. Storage: SQLite (notifications.db), shared by bot and GUI on the same machine.
   load_notifications() falls back to mock JSON if the DB doesn't exist yet.
5. "Segna come gestita" writes status:"resolved" to the DB (real, persistent).

Data contract (SQLite table: notifications)
-------------------------------------------
Column          Type      Notes
-----------     -------   ------------------------------------------------
id              INTEGER   primary key, auto-increment
id_thread       INTEGER   Kross thread id
id_message      INTEGER   dedup key — one notification per guest message
id_reservation  INTEGER
category        TEXT      intervento_host | riparazione | checkin_checkout
home            TEXT      apartment name (matches Kross name_room_type)
guest_name      TEXT
channel         TEXT      airbnb | booking | kross
check_in        TEXT      YYYY-MM-DD
check_out       TEXT      YYYY-MM-DD
message         TEXT      full guest message
summary         TEXT      escalation reason (produced by Claude)
created_at      TEXT      YYYY-MM-DD HH:MM:SS (set by storage.py)
status          TEXT      pending | resolved
handled_by      TEXT      reserved for multi-host phase
read_by         TEXT      reserved for multi-host phase

UNIQUE constraint on (id_thread, id_message) — prevents duplicate escalations.
Resolved records are kept in the DB (anti-re-notification safety net for the bot).

Filters (UI)
------------
- Stato prenotazione (combinable): Passate / Presente / Future  [GUI-computed]
- Categoria (single): Tutti / Riparazioni / Early-late check-in/out
- Casa (combinable): one per apartment
- Ordina per: Data notifica | Data prenotazione

Card content (Airbnb-style)
---------------------------
- Home name + stato & category badges
- Stay dates + guest name + channel
- Short summary (escalation reason from Claude)
- "Apri" button -> detail view -> "Segna come gestita"

MIGRATION PLAN: Streamlit → FastAPI + HTML/CSS on a single VPS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Why migrate
-----------
Streamlit Community Cloud has a read-only / ephemeral filesystem — notifications.db
can't live there. The bot runs on a different machine, so the GUI on Streamlit
Cloud can never see the DB file. The fix: move everything onto one server.

Target architecture (one cheap VPS, e.g. €5-10/month)
------------------------------------------------------
  script.py      runs as a background service (systemd or screen)
  notifications.db   single file on disk, shared by everything on this machine
  FastAPI        serves notifications as JSON (the "waiter" between DB and UI)
  HTML/CSS UI    the host dashboard, served by FastAPI as static pages

Why FastAPI + plain HTML (not React, not Streamlit)
---------------------------------------------------
- The UI is not complex: cards, three filters, a detail view, one button.
  Plain HTML + CSS is enough and gives full design control.
- FastAPI is pure Python — nothing new to learn on the server side.
- If React is ever needed later, the FastAPI backend stays exactly the same;
  only the HTML files get replaced.
- No filesystem limitations, no ephemeral storage, no third-party hosting
  dependency.

What changes vs what stays the same
------------------------------------
STAYS THE SAME:
  script.py      (no changes)
  storage.py     (no changes)
  notifications.db format (no changes)
  data contract / field names (no changes)

REPLACED:
  gui/app.py (Streamlit)  ->  a FastAPI app with HTML templates

The filter logic, booking_status computation, and mark_resolved call just move
from app.py into FastAPI route functions. The storage.py API is identical.

New project layout after migration
-----------------------------------
script.py
storage.py
notifications.db
web/
  main.py              # FastAPI app (routes + serves HTML)
  templates/
    index.html         # notification list with filters
    detail.html        # single notification detail + resolve button
  static/
    style.css          # card styles (same design as current Streamlit app)

FastAPI routes (minimum viable)
--------------------------------
  GET  /                          -> renders index.html with filtered list
  GET  /notification/{id}         -> renders detail.html for one notification
  POST /notification/{id}/resolve -> calls storage.mark_resolved(), redirects
  GET  /api/notifications         -> returns JSON (for future use / debugging)

How the filters work on the server side
----------------------------------------
The host opens / with optional query params, e.g.:
  /?category=riparazione&stato=presente&casa=Pellegrini+26
FastAPI reads the params, filters the DB rows, passes them to the template.
No JavaScript needed for the core flow.

Deployment steps (when ready)
------------------------------
1. Rent a VPS (DigitalOcean, Hetzner, OVH — any Ubuntu box).
2. Install Python, clone the repo, pip install fastapi uvicorn jinja2.
3. Run FastAPI:  uvicorn web.main:app --host 0.0.0.0 --port 80
4. Run the bot:  python script.py  (as a systemd service or in screen/tmux)
5. Point a domain at the VPS IP (optional but recommended).
6. Add HTTPS with Let's Encrypt (certbot) — mandatory before real guest data.
7. Add a simple login (HTTP Basic Auth or a password page) — mandatory before
   exposing to the public internet.
